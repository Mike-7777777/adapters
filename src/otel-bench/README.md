# OTelBench → Harbor Adapter

## Overview

This adapter brings [OTelBench](https://quesma.com/benchmarks/otel/) into the Harbor adapter index. OTelBench asks an agent to add OpenTelemetry instrumentation (traces, and in some tasks logs) to small services, then scores the result by running the service and inspecting the telemetry it emits.

- **Dataset size**: 25 tasks (the 26 upstream tasks minus one that no longer builds, see [Notes & Caveats](#notes--caveats))
- **Languages**: C++, Go, Java, JavaScript, .NET, PHP, Python, Ruby, Rust, Erlang, Swift
- **Task types**: single-program tracing (`*-simple`, `*-advanced`, `go-http-tracing`, `go-workflow-tracing`, `go-grpc-fix`), client/server context propagation (`*-distributed-context-propagation`), and three-service systems (`*-microservices*`)
- **Source**: [QuesmaOrg/otel-bench](https://github.com/QuesmaOrg/otel-bench), `datasets/otel`, pinned to commit [`bb6e21a`](https://github.com/QuesmaOrg/otel-bench/tree/bb6e21ad3caeceb82617dc5bf36e47deb33172ae), Apache-2.0
- **Scoring**: binary reward per task; `tests/test.sh` builds and runs the instrumented code, then pytest checks the exported spans and logs

OTelBench is written in Harbor's task format by its authors, so the adapter converts nothing. It fetches the tasks at the pinned commit, keeps every instruction, environment and test file byte for byte, adds the `[task]` table the registry needs, and makes sure each task has an oracle that passes.

## What is OTelBench?

OTelBench is an open-source benchmark from [Quesma](https://quesma.com) that measures whether coding agents can instrument existing code with OpenTelemetry, the kind of work a site reliability engineer does routinely. It launched on 2026-01-18 with 23 tasks and results for 14 models run through Harbor's `terminus-2` agent; the best model solved 29% of tasks ([launch post](https://quesma.com/blog/introducing-otel-bench/)). The repository has since grown to 26 tasks. The metric is the task pass rate: a task passes when its service builds, runs, and emits telemetry with the expected structure (span names and parent-child links, a single trace across services, service names, log records).

## Adapter Features

- Fetches `datasets/otel` at the pinned commit with a sparse, blobless clone; `--source-dir` reuses a local checkout instead.
- Copies only Harbor's task components (`task.toml`, `instruction.md`, `environment/`, `solution/`, `tests/`). Run summaries and spare collector configs stored next to the tasks upstream are left behind.
- Re-renders `task.toml` from `task-template/task.toml`: adds `[task].name` (`quesma/<task-id>`, the names already used by the `quesma/otel-bench` package on the Harbor Hub), credits the upstream task author in `[task].authors`, and carries every upstream value (timeouts, resources, difficulty, category, tags). Generation fails if an upstream `task.toml` contains a field the template does not carry.
- Supplies an oracle for `ruby-microservices`, which has none upstream, and applies small fixes to the upstream oracles that do not pass as shipped. All oracle changes live under `src/otel_bench/oracles/` and are listed in [Notes & Caveats](#notes--caveats).
- No custom agents. The upstream benchmark already runs on Harbor.

## Generated Task Structure

```
datasets/otel-bench/
└── {task-id}/                  # e.g. cpp-simple, go-microservices-logs
    ├── task.toml               # re-rendered: [task] table added, upstream values kept
    ├── instruction.md          # upstream, unchanged
    ├── environment/
    │   ├── Dockerfile          # upstream, unchanged
    │   └── code/               # service sources (microservices tasks), unchanged
    ├── solution/
    │   └── solve.sh            # upstream oracle, with adapter fixes where listed below
    └── tests/
        ├── test.sh             # upstream, unchanged; writes /logs/verifier/reward.txt
        └── test_*.py           # upstream, unchanged
```

## Run Evaluation / Harness

Run the registered dataset:

```bash
uvx --from harbor==0.25.0 harbor run -d quesma/otel-bench -a <agent> -m "<model>"
```

Run from a local copy generated by this adapter (see the next section):

```bash
uvx --from harbor==0.25.0 harbor run -c src/otel-bench/run_otel-bench.yaml          # oracle
uvx --from harbor==0.25.0 harbor run -p datasets/otel-bench -a <agent> -m "<model>" -n 2
uvx --from harbor==0.25.0 harbor trial start -p datasets/otel-bench/cpp-simple -a <agent> -m "<model>"
```

The tasks need outbound network access at build time and at test time, and Docker Engine 23 or newer (see [Installation / Prerequisites](#installation--prerequisites)).

## Usage: Create Task Directories

```bash
cd src/otel-bench
uv sync
uv run otel-bench --output-dir ../../datasets/otel-bench
```

| Flag | Meaning |
|------|---------|
| `--output-dir` | Where to write the task directories (default `datasets/otel-bench` under the current directory) |
| `--task-ids` | Generate only these task ids |
| `--limit` | Generate only the first N selected tasks |
| `--overwrite` | Replace task directories that already exist |
| `--source-dir` | A local copy of upstream `datasets/otel` at the pinned commit; skips the git fetch |
| `--list-tasks` | Print the task ids and exit |

## Notes & Caveats

Oracle validation used Harbor 0.25.0 on a 16-core x86-64 Linux host, three oracle runs and three no-op runs per task. Results are in the adapter PR.

**Excluded task (1 of 26).** `rust-distributed-context-propagation` no longer builds: its Dockerfile runs `cargo fetch` on `rust:1.82` without a `Cargo.lock`, and the dependency tree now resolves to `idna_adapter` 1.2.2, which needs the 2024 edition (Cargo 1.85 or newer). The break is in the task environment, so the adapter leaves the task out rather than change what the agent sees.

**Oracle changes.** Tests and environments are never modified. The adapter changes oracles only:

| Task | Upstream state | Adapter change |
|------|----------------|----------------|
| `ruby-microservices` | No oracle; upstream reports a 0% pass rate | New `solve.sh`. It sets `compression: 'none'` on the OTLP exporters because the collector the verifier uses (`otelite` v0.1.0) rejects gzip bodies, the Ruby exporter's default |
| `java-simple` | Oracle compiles against JARs in `lib/`, the verifier runs a bare `javac Demo.java` | Appended step unpacks the JARs into the working directory so the bare command resolves them |
| `php-distributed-context-propagation` | Oracle calls `python3`, which the `php:8.2-cli` image lacks; the script aborts and leaves its server and collector on the verifier's ports. Its `server.php` also omits the start-up line the test looks for | Prepended step installs `python3`; appended step logs the start-up line with `error_log()` |
| `python-distributed-context-propagation` | `server.py` calls `server.shutdown()` from its SIGTERM handler on the serving thread and deadlocks, so the captured server output stays empty | Appended step removes that call; `sys.exit(0)` in the handler then stops the server and flushes its output |
| `java-microservices`, `net-microservices` | The verifier sends its request one second after `make start` launches the gateway (the script reads `echo 5` where `sleep 5` was meant); the JVM gateway is never listening that soon (shipped oracle: 0 of 3 on an idle host), and the .NET gateway makes it on an idle host but not under moderate load (2 of 3 failed at a load average of 13 on 16 cores) | Appended step makes each service's `make start` wait until its port accepts connections. `ruby-microservices` gets the same step: its gateway needs about one second |
| `cpp-advanced` | `app.cpp` prints from several threads with chained `<<`; pieces of lines interleave and the verifier's substring checks on the console output fail in a fraction of runs | Appended step makes each print statement write its line in one locked call |

**Known upstream behaviour kept as is.**

- The one-second start-up window and the interleaved console output above also apply to agents: a correct solution to `java-microservices`, `net-microservices`, `ruby-microservices` or `cpp-advanced` can score 0. `net-microservices` passes on an idle host. The other ten microservices tasks start fast enough on a host that is not oversubscribed; run with low concurrency.
- Verifiers rely on fixed sleeps and on downloads at test time (uv, pytest, and for the context-propagation tasks an OpenTelemetry Collector release), so results depend on network access and host load.
- Dockerfiles install unpinned toolchains and dependencies (`uv` installer, `rustup` stable, language package managers). Builds can drift.
- The tasks are public together with their reference solutions, and agents have network access.
- Upstream commit `5afbba1` (the only commit after the pin) prepends a canary line to every task file, including `instruction.md` and source files the agent reads. The pin stays one commit earlier, which is also the content the Hub package `quesma/otel-bench` was published from.

## Installation / Prerequisites

- Docker Engine 23.0 or newer (or any builder with BuildKit 0.10+): 15 Dockerfiles use heredocs and carry no `# syntax=` line, so older engines fail with `dockerfile parse error ... unknown instruction`.
- x86-64 host. The context-propagation verifiers download `linux_amd64` collector binaries.
- Outbound network access for builds and tests.
- Harbor: `uv tool install harbor` (validated with 0.25.0). Adapter: Python 3.11+, `uv`, `git`.
- 4 CPUs and 8 GB of memory per concurrent trial for the larger tasks.

## Troubleshooting

- `dockerfile parse error ... unknown instruction`: the Docker engine predates heredoc support. Upgrade Docker, or build with a newer BuildKit: `docker buildx create --name bk --driver docker-container && export BUILDX_BUILDER=bk`.
- `EnvironmentStartTimeoutError` on `swift-microservices`, `rust-microservices` or `cpp-distributed-context-propagation`: these images compile toolchains or SDKs and can exceed the build timeout on a busy host. Lower `-n` or pass `--environment-build-timeout-multiplier`.
- Microservices tasks fail with zero traces although the code is instrumented: the request was sent before the gateway was listening. Lower `-n`.
- `./gradlew: Permission denied` in `java-microservices`: the task copy lost its executable bits (the Hub package published before this adapter has none). Regenerate with this adapter, or `chmod +x environment/code/*/gradlew`.
- `git clone` fails during generation: pass `--source-dir` with a local checkout of the pinned commit.
